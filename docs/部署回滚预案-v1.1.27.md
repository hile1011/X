## 二、版本回退方案

### 场景 A：应用异常（服务无法启动 / 健康检查失败 / 功能严重 Bug）— 代码回滚

```bash
# 1. 一键回滚到部署前代码（本地执行）
bash scripts/deploy-remote.sh --rollback

# 2. 验证（脚本自动执行，也可手动）
ssh root@8.136.117.41 'curl -s http://localhost:3003/api/health'   # 期待 {"status":"ok"}
```

若 `/tmp` 备份被清理，改用 GitHub 标签重建：

```bash
# 本地取回上一版本代码并重新部署
git checkout v1.1.26
bash scripts/deploy-remote.sh --skip-push --skip-tag
git checkout main
```

### 场景 B：数据异常（订单号数据损坏等）— 数据恢复

本版本仅改写"新建/复制订单"的订单号生成逻辑，不改历史数据；若极端情况下需要恢复数据：

```bash
# 服务器上执行（先停服避免写入，再导入备份）
ssh root@8.136.117.41 '
  pm2 stop X-api
  PW=$(grep "^MYSQL_PASSWORD=" /usr/X-prod/.env | cut -d= -f2-)
  gunzip < /root/db-backups/quote_system_prod_pre_v1.1.27_20260902_001555.sql.gz | mysql -uroot -p"$PW" quote_system_prod
  pm2 start X-api
  curl -s http://localhost:3003/api/health
'
```

> 注意：数据恢复会丢失备份时间点（2026-09-02 00:15）之后产生的业务数据，仅作为最后手段。

### 场景 C：仅回退应用代码、保留数据（推荐的最小回滚）

本次变更无 schema 变更、无数据回填，代码回滚与数据完全兼容，**优先使用场景 A**。

## 三、数据备份策略（本次已执行 + 长期策略）

- **部署前强制备份**：每次生产部署前执行 mysqldump 全量备份至 `/root/db-backups/`，命名含目标版本号（`*_pre_v1.1.27_*.sql.gz`），与部署日志对应可追溯。
- **涉及数据库迁移的部署**（本次不涉及）：遵循 `docs/数据库版本管理规范.md`——迁移必须提供 `down` 回滚函数；生产执行前备份；回滚先执行迁移 down 再恢复代码。
- **保留策略**：`/root/db-backups/` 建议至少保留最近 5 个版本的备份，定期同步至异地/对象存储。

## 四、应急恢复流程（联系方式与排查路径）

1. **发现异常**：健康检查失败（`/api/health` 非 ok）/ 用户反馈核心功能不可用 / PM2 状态非 online。
2. **快速止损**：优先执行场景 A 一键回滚（停机窗口约 10-30 秒）。
3. **定位排查**：
   - 应用日志：`ssh root@8.136.117.41 'pm2 logs X-api --lines 200'`
   - 部署日志：本地 `data/logs/deploy-*.log`
   - 数据检查：`SELECT id, quote_number, updated_at FROM quotes ORDER BY updated_at DESC LIMIT 10;`
4. **数据受损时**：执行场景 B 恢复备份（评估数据丢失窗口后决策）。
5. **恢复后**：修复问题 → 重走发布流程（测试全绿 → 备份 → 部署 → 验证）→ 新版本打新 tag，禁止复用/移动已发布 tag。
