# 数据库版本管理规范

> **版本**：V1.0
> **生效日期**：2026-08-09
> **适用项目**：报价跟单系统（quote-order-system）
> **当前 Schema 版本**：v12

---

## 1. 总则

### 1.1 目的

本规范旨在建立一套统一、可追溯、可回滚的数据库版本管理机制，确保数据库结构变更在开发、测试、生产环境中平滑升级，避免数据丢失和服务中断。

### 1.2 核心原则

| 原则 | 说明 |
|------|------|
| **双轨维护** | 同时维护全量脚本（最新完整快照）和增量脚本（版本间变更），两者互为校验 |
| **向前兼容** | 增量迁移必须支持平滑升级，生产环境升级期间不中断服务 |
| **可回滚** | 每个增量迁移必须提供 `down` 函数，支持版本回退 |
| **幂等执行** | 所有 DDL 使用 `CREATE TABLE IF NOT EXISTS`，DML 使用 `INSERT IGNORE`，可安全重复执行 |
| **版本追溯** | 通过 `schema_migrations` 表记录已执行的迁移版本，任何环境可查询当前版本 |
| **事务保护** | 每个迁移的 `up`/`down` 在数据库事务中执行，失败自动回滚 |

### 1.3 适用范围

- 所有涉及数据库表结构变更（DDL）的开发任务
- 所有涉及种子数据（DML）初始化的变更
- 开发、测试、生产三个环境的数据库同步

## 2. 目录结构与脚本分类

### 2.1 目录结构

```
db/
├── schema/                         # 全量脚本（最新完整快照）
│   ├── schema_v12.sql              # 当前版本 v12 的完整结构和种子数据
│   └── schema_v11.sql              # 历史版本（归档，不再维护）
│
├── migrations/                     # 增量脚本（SQL 备份格式，只读归档）
│   ├── v001_initial-schema.sql     # v1 初始建表（从 TypeScript 迁移导出）
│   ├── v007_add-product-code.sql
│   ├── v012_add-auth-rbac.sql
│   └── README.md                   # 增量脚本索引
│
└── seed/                           # 独立种子数据脚本
    └── seed_dev.sql                # 开发环境演示数据（非生产数据）

api/migrations/
└── index.ts                        # 增量迁移源码（TypeScript，实际执行入口）
                                    # 包含 MigrationRunner 类和 migrations 数组
```

### 2.2 脚本分类

| 类型 | 位置 | 格式 | 用途 | 维护时机 |
|------|------|------|------|----------|
| **全量脚本** | `db/schema/` | `.sql` | 新环境初始化、结构参照、快速重建 | 每次发布新版本时更新 |
| **增量迁移源码** | `api/migrations/index.ts` | `.ts` | 实际执行的迁移逻辑（含复杂数据处理） | 每次数据库变更时新增 |
| **增量SQL备份** | `db/migrations/` | `.sql` | 迁移逻辑的 SQL 归档（只读，供审查） | 从 TypeScript 迁移导出 |
| **种子数据** | `db/seed/` | `.sql` | 开发环境演示数据 | 按需维护 |

### 2.3 两类脚本的关系

```
全量脚本 (db/schema/schema_vN.sql)
    ↕ 互为校验
增量脚本 (api/migrations/index.ts)
    │
    ├── 全量脚本 = 所有增量脚本的 up 函数按版本顺序叠加的结果
    ├── 增量脚本 = 全量脚本按版本拆分的变更步骤
    └── 每次发布新版本时，两者必须同步更新并通过一致性校验
```

## 3. 命名规范

### 3.1 全量脚本

```
db/schema/schema_v{版本号}.sql
```

- 示例：`schema_v12.sql`、`schema_v13.sql`
- 版本号与 `CURRENT_SCHEMA_VERSION` 保持一致

### 3.2 增量迁移（TypeScript）

在 `api/migrations/index.ts` 的 `migrations` 数组中定义：

```typescript
{
  version: 13,                          // 版本号，递增 +1
  name: 'add-xxx-table',               // 简短英文名，kebab-case
  description: 'V0.7：新增 XXX 功能表', // 中文描述，含版本标签
  up: async (db) => { ... },
  down: async (db) => { ... },
}
```

**命名规则**：
- `name`：小写英文 + kebab-case，描述变更内容（如 `add-auth-rbac`、`add-quote-status-index`）
- `description`：中文描述，以功能版本标签开头（如 `V0.7：`）
- `version`：严格递增的整数，不跳号

### 3.3 增量SQL备份

```
db/migrations/v{三位版本号}_{name}.sql
```

- 示例：`v012_add-auth-rbac.sql`
- 版本号补零至三位，便于按文件名排序

### 3.4 常量定义

```typescript
// api/migrations/index.ts
export const CURRENT_SCHEMA_VERSION = 13  // 每次新增迁移时 +1
```

## 4. 版本号管理

### 4.1 版本号规则

```
Schema 版本号：纯整数递增（1, 2, 3, ..., 12, 13, ...）
应用版本号： 语义化版本（如 1.1.6 → 1.2.0）
```

- Schema 版本号与应用版本号独立管理
- 每次数据库结构变更，Schema 版本号 **必须 +1**
- 版本号不可跳号（如 v11 → v13 是禁止的）
- 版本号不可复用（已发布的版本号不可重新定义）

### 4.2 版本追踪机制

```
schema_migrations 表
┌─────────┬─────────────────────────┬──────────────────────┬─────────────────────┐
│ version │ name                    │ description          │ applied_at          │
├─────────┼─────────────────────────┼──────────────────────┼─────────────────────┤
│       1 │ initial-schema          │ 初始化数据库表结构    │ 2026-07-01 10:00:00 │
│      12 │ add-auth-rbac           │ V0.6：新增RBAC...    │ 2026-08-09 12:00:00 │
└─────────┴─────────────────────────┴──────────────────────┴─────────────────────┘
```

- `MigrationRunner.getCurrentVersion()` 返回已执行的最高版本号
- `MigrationRunner.getPendingMigrations()` 返回待执行的迁移列表
- 应用启动时自动检测并执行待执行迁移（见 [§8 自动化策略](#8-自动化执行策略)）

### 4.3 版本号与发布流程

```
开发阶段：
  1. 新增迁移 → CURRENT_SCHEMA_VERSION +1
  2. 编写 up/down 函数 → 本地测试通过
  3. 更新全量脚本 → db/schema/schema_vN.sql
  4. 提交代码 → Git commit

发布阶段：
  5. 推送至 GitHub → git push
  6. 部署脚本拉取代码 → 执行 npm run db:migrate
  7. 验证 schema_migrations 版本 → 健康检查
  8. 重启后端服务 → PM2 reload
```

## 5. 增量迁移脚本编写标准

### 5.1 结构模板

```typescript
{
  version: 13,
  name: 'add-xxx-table',
  description: 'V0.7：新增 XXX 功能表',

  up: async (db: any) => {
    // 1. DDL：建表/加列/加索引（使用 IF NOT EXISTS）
    await db.exec(`
      CREATE TABLE IF NOT EXISTS xxx (
        id VARCHAR(64) PRIMARY KEY,
        name VARCHAR(255) NOT NULL,
        created_at DATETIME DEFAULT CURRENT_TIMESTAMP
      )
    `)

    // 2. DML：种子数据（使用 INSERT IGNORE）
    const stmt = db.prepare(
      'INSERT IGNORE INTO xxx (id, name) VALUES (?, ?)'
    )
    await stmt.run('xxx-1', '默认项')

    // 3. 数据迁移（如需从老数据转换）
    const rows = await db.prepare('SELECT id, old_field FROM quotes').all()
    for (const row of rows) {
      await db.prepare('UPDATE quotes SET new_field = ? WHERE id = ?')
        .run(row.old_field, row.id)
    }
  },

  down: async (db: any) => {
    // 逆序撤销 up 的所有操作
    await db.exec('DROP TABLE IF EXISTS xxx')
  },
}
```

### 5.2 编写规则

| 规则 | 要求 | 示例 |
|------|------|------|
| DDL 幂等 | 所有 CREATE/ALTER 使用 IF NOT EXISTS | `CREATE TABLE IF NOT EXISTS ...` |
| DML 幂等 | 所有 INSERT 使用 IGNORE 或 ON DUPLICATE KEY | `INSERT IGNORE INTO ...` |
| 不可逆操作慎用 | DROP COLUMN / DROP TABLE 需先备份数据 | down 函数中才允许 DROP |
| 数据迁移分批 | 大表数据迁移需分批处理（每批 ≤ 1000 行） | `LIMIT 1000 OFFSET ?` |
| 不依赖外部状态 | 迁移不应依赖 HTTP 请求或文件系统 | 仅操作数据库 |
| 字符集统一 | 所有表使用 utf8mb4 | `DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci` |
| 索引命名 | 以 `idx_` 开头，包含表名和字段名 | `idx_quotes_status` |

### 5.3 down 函数要求

- **必须提供**，即使是最简单的 `DROP TABLE IF EXISTS`
- 逆序撤销 up 的所有操作
- down 函数不负责数据恢复（如 up 中删除了列，down 无法恢复数据）
- 对于数据迁移类操作，down 函数应记录警告日志

### 5.4 禁止事项

```
❌ 直接修改已发布的迁移（已执行过的 version 不可变更）
❌ 跳过版本号（v11 → v13）
❌ 在迁移中调用外部 API 或文件系统
❌ 使用 SELECT * 做数据迁移（列顺序可能变化）
❌ 在迁移中硬编码敏感信息（密码、密钥）
❌ 迁移执行时间超过 30 秒（大表需分批）
```

## 6. 全量 Schema 脚本编写标准

### 6.1 内容要求

全量脚本必须包含以下完整内容，按顺序排列：

```
1. 文件头注释（版本、日期、用途、使用方法）
2. SET FOREIGN_KEY_CHECKS = 0
3. schema_migrations 表定义
4. 所有业务表 CREATE TABLE IF NOT EXISTS（按依赖顺序）
5. SET FOREIGN_KEY_CHECKS = 1
6. 种子数据 INSERT IGNORE（默认产品、权限、角色、管理员）
7. schema_migrations 版本记录（标记所有版本为已执行）
8. 验证查询（注释形式）
```

### 6.2 生成方式

全量脚本有两种生成方式，结果必须一致：

**方式一：从数据库导出（推荐）**
```bash
# 导出结构
mysqldump -u root -h 127.0.0.1 <database> --no-data --skip-comments \
  --skip-add-drop-table --routines > /tmp/schema_raw.sql

# 导出种子数据（仅默认数据表）
mysqldump -u root -h 127.0.0.1 <database> \
  products permissions roles role_permissions user_roles \
  --no-create-info --skip-comments --complete-insert >> /tmp/schema_raw.sql

# 手动清理并添加文件头、schema_migrations 记录
```

**方式二：从增量迁移合成**
```bash
# 依次执行所有 up 函数到全新数据库，再导出
npm run db:reset  # 重置数据库（DROP ALL + MIGRATE）
# 然后执行方式一的导出命令
```

### 6.3 更新时机

全量脚本在以下情况必须更新：

- 每次发布新版本（`CURRENT_SCHEMA_VERSION` 变更后）
- 新增或修改表结构后
- 新增或修改种子数据后

### 6.4 一致性校验

发布前必须验证全量脚本与增量迁移的一致性：

```bash
# 1. 用全量脚本创建全新数据库
mysql -u root -e "CREATE DATABASE verify_schema"
mysql -u root verify_schema < db/schema/schema_v13.sql

# 2. 检查表数量、字段、种子数据数量
mysql -u root verify_schema -e "
  SELECT COUNT(*) FROM information_schema.tables WHERE table_schema = 'verify_schema';
  SELECT COUNT(*) FROM permissions;
  SELECT version FROM schema_migrations ORDER BY version DESC LIMIT 1;
"

# 3. 与现有数据库对比
# 表数量、字段列表、索引列表应完全一致
```

## 7. 审核流程

### 7.1 迁移审核清单

每次新增数据库迁移时，开发者必须完成以下审核清单：

```
□ 版本号正确
  □ version = CURRENT_SCHEMA_VERSION + 1
  □ CURRENT_SCHEMA_VERSION 已更新
  □ 不存在跳号或复用

□ up 函数
  □ 所有 DDL 使用 IF NOT EXISTS
  □ 所有 INSERT 使用 IGNORE
  □ 大表数据迁移分批处理
  □ 执行时间 < 30 秒（预估）

□ down 函数
  □ 已提供
  □ 逆序撤销 up 的所有操作
  □ DROP 操作使用 IF EXISTS

□ 全量脚本
  □ db/schema/schema_vN.sql 已更新
  □ 包含新表/新字段
  □ 包含新种子数据
  □ schema_migrations 记录已更新

□ 测试
  □ 本地执行 up → 验证数据 → 执行 down → 验证回滚
  □ npm run db:migrate 成功
  □ npm test 全部通过
  □ 全量脚本在空数据库上可执行

□ 文档
  □ docs/数据库文档.md 已更新（表清单、字段说明）
  □ Git commit message 包含迁移版本号和描述
```

### 7.2 审核流程

```
开发者提交 PR / 代码变更
       │
       ▼
┌──────────────────┐     不通过      ┌──────────────────┐
│ 自动化检查        │ ──────────────→ │ 退回修改          │
│ - tsc --noEmit   │                 │ - 修复编译错误     │
│ - npm test        │                 │ - 修复测试失败     │
│ - 全量脚本校验     │                 └──────────────────┘
└────────┬─────────┘
         │ 通过
         ▼
┌──────────────────┐     不通过      ┌──────────────────┐
│ 人工审核          │ ──────────────→ │ 退回修改          │
│ - 迁移编写规范     │                 │ - 按审核意见修改   │
│ - down 函数完整性  │                 └──────────────────┘
│ - 种子数据正确性   │
│ - 性能影响评估     │
└────────┬─────────┘
         │ 通过
         ▼
   合并到主分支
```

## 8. 自动化执行策略

### 8.1 自动迁移机制

应用启动时（`api/db.ts` 模块加载）自动执行迁移：

```typescript
// api/db.ts 模块级代码（启动时执行一次）
const currentVersion = await runner.getCurrentVersion()
if (currentVersion < CURRENT_SCHEMA_VERSION) {
  console.log(`[DB] Schema version ${currentVersion} -> ${CURRENT_SCHEMA_VERSION}, running migrations...`)
  const result = await runner.migrate()
  // ...
}
```

**执行逻辑**：
1. 读取 `schema_migrations` 表获取已执行版本
2. 对比 `CURRENT_SCHEMA_VERSION` 判断是否有待执行迁移
3. 按版本号升序依次执行待执行迁移的 `up` 函数
4. 每个迁移在独立事务中执行，失败自动回滚
5. 成功后在 `schema_migrations` 表记录版本号

### 8.2 手动执行命令

```bash
# 执行所有待执行的迁移
npm run db:migrate

# 重置数据库（DROP ALL + 重新迁移）— 仅开发/测试环境
npm run db:reset

# 填充演示数据 — 仅开发环境
npm run db:seed
```

### 8.3 部署集成

生产环境部署脚本（`scripts/deploy-remote.sh`）中的迁移执行顺序：

```bash
# 1. 拉取最新代码
git pull origin main

# 2. 执行数据库迁移（在重启服务之前）
npm run db:migrate

# 3. 验证迁移结果
MYSQL_VERSION=$(mysql -u root -p*** -e "SELECT version FROM schema_migrations ORDER BY version DESC LIMIT 1;" | tail -1)
if [ "$MYSQL_VERSION" != "$EXPECTED_VERSION" ]; then
  echo "[ERROR] 数据库版本不匹配: 期望 $EXPECTED_VERSION, 实际 $MYSQL_VERSION"
  exit 1
fi

# 4. 构建前端
npm run build:frontend

# 5. 重启后端服务（PM2 热重载，零停机）
pm2 reload quote-system-api

# 6. 健康检查
curl -f http://localhost:3003/api/health || exit 1
```

### 8.4 零停机升级策略

```
迁移类型         │ 零停机策略
────────────────┼──────────────────────────────────────────
新增表           │ 直接执行，不影响运行中的服务
新增列（可空）    │ 直接执行，旧代码忽略新列
新增列（非空）    │ 先加列设默认值 → 部署新代码 → 移除默认值
删除列           │ ① 部署代码（停止使用该列）→ ② 下次发布执行 DROP
重命名列         │ ① 新增列 → ② 数据迁移 → ③ 部署代码 → ④ 删除旧列
修改列类型       │ ① 新增列 → ② 双写迁移 → ③ 部署代码 → ④ 删除旧列
大表加索引        │ 使用 ALGORITHM=INPLACE, LOCK=NONE 避免锁表
```

## 9. 回滚方案

### 9.1 回滚命令

```bash
# 回滚到指定版本（执行 > N 的所有 down 函数）
# 在 api/migrate.ts 中添加 --rollback 参数支持
npx tsx -e "
  import { db } from './api/db'
  await db.runner.rollback(11)  // 回滚到 v11
  process.exit(0)
"

# 完全重置（回滚到 v0，删除所有表）
npm run db:reset
```

### 9.2 回滚决策树

```
迁移执行失败
    │
    ├── 事务自动回滚（MigrationRunner 已处理）
    │   → 检查错误日志 → 修复迁移代码 → 重新执行
    │
    └── 迁移成功但业务异常
        │
        ├── 影响范围小 → 手动 rollback 到上一版本
        │   → 修复代码 → 重新发布
        │
        └── 影响范围大 → 启用全量脚本恢复
            → 从备份恢复数据库 → 执行上一版本的全量脚本
```

### 9.3 数据备份策略

```
环境      │ 备份频率          │ 备份方式                    │ 保留期
─────────┼─────────────────┼────────────────────────────┼──────────
开发环境  │ 不需要            │ -                          │ -
测试环境  │ 每次测试前        │ mysqldump                  │ 3 天
生产环境  │ 每次发布前（必须）│ mysqldump + binlog         │ 30 天
```

**生产环境发布前备份命令**：
```bash
# 结构 + 数据全量备份
mysqldump -u root -p*** --single-transaction --routines --triggers \
  quote_system_prod > /backup/quote_system_prod_$(date +%Y%m%d_%H%M%S).sql

# 验证备份文件
mysql -u root -p*** -e "SELECT COUNT(*) FROM quotes;" quote_system_prod
# 对比备份文件中的记录数
grep -c "INSERT INTO" /backup/quote_system_prod_*.sql
```

### 9.4 回滚不可逆场景处理

以下操作回滚后**无法恢复数据**，必须提前备份：

- `DROP TABLE` — down 函数重建表结构，但数据丢失
- `DROP COLUMN` — down 函数重新加列，但数据丢失
- `DELETE FROM` — down 函数无法恢复删除的行
- `ALTER COLUMN` 修改类型 — 精度丢失不可逆

**处理原则**：执行此类操作前，必须先执行数据备份，并在迁移描述中标注 `⚠️ 不可逆操作`。

## 10. 环境管理

### 10.1 三环境对照

| 环境 | 数据库名 | 用途 | 迁移执行方式 | 重置权限 |
|------|----------|------|-------------|----------|
| 开发 | `quote_system_dev` | 本地开发调试 | 自动迁移（启动时） | 允许 `db:reset` |
| 测试 | `quote_system_test` | 单元测试、集成测试 | 测试前自动迁移 | 允许 `db:reset` |
| 生产 | `quote_system_prod` | 线上服务 | 部署脚本手动执行 | **禁止** `db:reset` |

### 10.3 环境同步规则

```
开发环境                         测试环境                         生产环境
    │                               │                               │
    │  新增迁移 + 本地测试            │                               │
    │ ─────────────────────────────→ │                               │
    │                               │  运行测试套件（自动迁移）        │
    │                               │ ─────────────────────────────→ │
    │                               │                               │  发布前备份
    │                               │                               │  执行 db:migrate
    │                               │                               │  验证 + 健康检查
    │                               │                               │  PM2 reload
```

**同步规则**：
1. 迁移代码必须先在开发环境测试通过
2. 测试环境通过全部测试用例后，才可发布到生产
3. 生产环境执行迁移前必须备份数据库
4. 三个环境的 `schema_migrations` 表内容应完全一致（版本号相同）

describe('迁移 v13 - add-xxx-table', () => {

  })

    // 验证表不存在

  })
