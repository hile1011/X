## 3. 部署步骤

### 3.1 标准部署（推荐：deploy-remote.sh）

```bash
# 一键部署：本地构建 → 上传 → 远程重启 → 健康检查（失败自动回滚代码）
bash scripts/deploy-remote.sh
```

脚本自动完成：

1. 本地构建前端（Vite → `dist/`）与后端（tsc → `api/dist/`）
2. 打包源码（排除 node_modules/.env/.git 等）与构建产物，SCP 上传
3. 远程备份当前代码到 `/tmp/X-backup-*.tar.gz`
4. 解压新代码与产物，`npm install --omit=dev`
5. `pm2 restart X-api --update-env && pm2 save`
6. 健康检查 + 前端页面 + API 性能验证，**失败自动回滚**

常用选项：

| 选项 | 用途 |
|------|------|
| `--skip-build` | 复用已有 `dist/`、`api/dist/`（如手动构建过） |
| `--skip-push` | 跳过 git commit/push（已提交时） |
| `--skip-tag` | 跳过版本号递增与打标签（版本/tag 已手动完成时） |
| `--version vX.Y.Z` | 指定版本号 |
| `--rollback` | 回滚到上一版本 |
| `--dry-run` | 只打印命令不执行 |

### 3.2 含数据库迁移的部署（完整顺序）

> **顺序原则：先备份 → 部署代码 → 执行迁移 → 验证数据 → 验证服务。**
> 迁移均为幂等设计，服务重启后短暂窗口内新代码可兼容旧 schema（新增列/表不影响旧查询），因此"先部署后迁移"窗口风险最小。

```bash
# ── 阶段 0：部署前检查（§2 清单全部通过）──
npm run check && npm test

# ── 阶段 1：生产库备份（必须，见 §4.1）──
# （deploy-remote.sh 的代码备份不含数据库，数据库备份须单独执行）

# ── 阶段 2：部署代码 ──
bash scripts/deploy-remote.sh --skip-tag    # 版本与 tag 已按提交规范手动完成时

# ── 阶段 3：执行迁移 ──
ssh root@8.136.117.41 'cd /usr/X-prod && node api/dist/migrate.js'
# 期望输出：[Migration] 已执行: ✅ v00NN - <name> ... [Migration] 完成，当前版本: vN

# ── 阶段 4：存量数据迁移结果验证（见 §5.3）──

# ── 阶段 5：部署后验证（见 §5）──
```

> 历史范例：v1.1.25（DB v16→v23 + pendingAmount 回填）、v1.1.28（DB v23→v24 + 做货任务存量迁移）。

### 3.3 手动部署（deploy-remote.sh 不可用时兜底）

```bash
# 1. 本地构建
npm run build:frontend && npm run build:backend

# 2. 打包（源码包排除敏感与冗余目录；产物包只含 dist/ api/dist/）
tar czf /tmp/X-src-$(date +%Y%m%d_%H%M%S).tar.gz \
  --exclude='node_modules' --exclude='.env*' --exclude='.git' --exclude='dist' \
  --exclude='api/dist' --exclude='tests' --exclude='docs' --exclude='data' .
tar czf /tmp/X-dist-$(date +%Y%m%d_%H%M%S).tar.gz dist/ api/dist/

# 3. 远程备份 + 上传 + 解压 + 重启
ssh root@8.136.117.41 'cd /usr/X-prod && tar czf /tmp/X-backup-$(date +%Y%m%d_%H%M%S).tar.gz \
  --exclude=node_modules --exclude=.env --exclude=dist_backup_* .'
scp /tmp/X-src-*.tar.gz /tmp/X-dist-*.tar.gz root@8.136.117.41:/tmp/
ssh root@8.136.117.41 'cd /usr/X-prod && \
  tar xzf /tmp/X-src-<时间戳>.tar.gz && rm -rf dist api/dist && \
  tar xzf /tmp/X-dist-<时间戳>.tar.gz && \
  ln -sf /usr/X-prod/.env api/.env && \
  npm install --omit=dev && pm2 restart X-api --update-env && pm2 save'

# 4. 后续按 §3.2 阶段 3-5 执行迁移与验证
```

### 3.4 部署窗口与停机控制

- PM2 restart 为秒级滚动重启，常规发布停机 < 10 秒
- 含 DDL 的迁移（ALTER TABLE 大表）在低峰执行；本项目 quotes 表规模小（< 1 万行），单迁移 < 30 秒
- 部署期间避免同时执行其他运维操作（如手动改库）

## 4. 数据库备份与恢复流程

### 4.1 部署前备份（强制）

```bash
ssh root@8.136.117.41 '
  mkdir -p /root/db-backups
  PW=$(grep "^MYSQL_PASSWORD=" /usr/X-prod/.env | cut -d= -f2-)
  F=/root/db-backups/quote_system_prod_pre_vX.Y.Z_$(date +%Y%m%d_%H%M%S).sql.gz
  mysqldump -uroot -p"$PW" --single-transaction --routines --triggers quote_system_prod | gzip > "$F"
  echo "备份完成: $F ($(du -h $F | cut -f1))"
'
```

要求：

- 命名规则：`quote_system_prod_pre_<版本>_<时间戳>.sql.gz`，与发布版本对应，便于回滚定位
- 备份后立即验证：`gunzip -t <文件>` 校验完整性；记录文件路径到发布记录
- `/root/db-backups/` 长期保留（至少最近 10 个版本）；`/tmp/` 下的临时备份随时可能被清理，仅作短期兜底

### 4.2 数据恢复流程

```bash
ssh root@8.136.117.41 '
  pm2 stop X-api                       # 1. 停服，避免恢复期间写入
  PW=$(grep "^MYSQL_PASSWORD=" /usr/X-prod/.env | cut -d= -f2-)
  gunzip < /root/db-backups/<备份文件>.sql.gz | \
    mysql -uroot -p"$PW" quote_system_prod   # 2. 导入备份（覆盖当前数据）
  pm2 start X-api && sleep 3 && \
  curl -s http://localhost:3003/api/health   # 3. 重启并验证
'
```

> **注意**：全量导入会覆盖备份时点之后的全部数据（含备份后新增订单）。恢复前先评估损失范围；若仅个别表损坏，可从备份中抽取该表的 INSERT 语句定向恢复。

### 4.3 迁移级回退（保留新数据的回滚）

当只需回退 schema 而尽量保留新数据时，优先使用迁移 `down`（而非整库恢复）：

```bash
ssh root@8.136.117.41 'cd /usr/X-prod && node -e "
  // 使用 MigrationRunner.rollback(targetVersion)，参考 api/dist/migrate.js
"'
```

前提：`down` 函数经过测试（migration-*.test.ts 回滚用例）；有损 down（如删列丢数据）禁止在生产直接执行，必须走 §4.2 + 人工评估。

## 5. 部署后验证方法

### 5.1 标准验证清单（每次部署必做）

```bash
ssh root@8.136.117.41 '
  echo "── 1. 健康检查 ──" && curl -s http://localhost:3003/api/health
  echo "── 2. 前端页面 ──" && curl -s http://localhost:3003/ | grep -o "<title>[^<]*</title>"
  echo "── 3. API 响应 ──" && curl -s -o /dev/null -w "HTTP %{http_code} 耗时 %{time_total}s\n" http://localhost:3003/api/quotes
  echo "── 4. PM2 状态 ──" && pm2 list | grep X-api
  echo "── 5. 错误日志 ──" && pm2 logs X-api --err --lines 20 --nostream
  echo "── 6. 启动日志 ──" && pm2 logs X-api --out --lines 10 --nostream
'
```

| # | 验证项 | 通过标准 |
|---|--------|---------|
| 1 | 健康检查 | `{"status":"ok"}` |
| 2 | 前端页面 | 返回 `<title>报价跟单系统</title>` 且为新构建版本 |
| 3 | API 响应 | 未认证请求返回 401（认证拦截正常），耗时 < 100ms |
| 4 | PM2 | `X-api` online，version 为新版本号 |
| 5 | 错误日志 | 无新增 Error / 堆栈 |
| 6 | 启动日志 | `[DB] Schema at latest version vN`（含迁移时）、`[Server] 运行于 0.0.0.0:3003` |

### 5.2 含迁移发布的附加验证

```bash
# 迁移版本记录
ssh root@8.136.117.41 'cd /usr/X-prod && set -a && source .env && set +a && \
  mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" "$MYSQL_DATABASE" \
  -e "SELECT version, name, applied_at FROM schema_migrations ORDER BY version DESC LIMIT 5;"'
```

- [ ] `schema_migrations` 新增对应版本记录，无跳版
- [ ] 新表/新列存在（`SHOW TABLES` / `SHOW COLUMNS`）
- [ ] 种子数据正确（权限、角色、默认数据条数）

### 5.3 存量数据迁移验证（抽样 + 全量一致性校验）

以"公式/规则回填"类迁移为例（如 v1.1.25 的 pendingAmount 回填、v1.1.28 的做货任务迁移）：

```sql
-- ① 总量核对：迁移目标行数 = 源数据行数（或符合预期过滤条件）
SELECT COUNT(*) FROM <目标表> WHERE <迁移条件>;

-- ② 抽样比对：随机/首尾若干条，人工核对字段值
SELECT * FROM <目标表> LIMIT 10;

-- ③ 全量一致性校验：目标值 vs 期望值，不匹配数必须为 0
SELECT COUNT(*) AS mismatch FROM <表>
WHERE ABS(<实际字段> - <期望公式>) > 0.01;
```

- mismatch 必须为 0（或逐条解释差异原因）才视为迁移成功
- 反向校验：不该有值的地方必须为空/0（如非目标状态记录的 pendingAmount = 0）

### 5.4 业务冒烟测试（关键流程人工抽查）

按本次改动范围，在生产环境用真实账号抽查：

- 登录 / 权限（新权限对角色生效）
- 本次新增功能的增删改查（如做货流程任务的保存、甘特图渲染）
- 相邻关联功能（如订单状态流转、导出）
- 收款/金额类改动：抽 3-5 单人工核对金额计算

## 6. 回滚机制

### 6.1 回滚决策标准

| 场景 | 动作 |
|------|------|
| 服务无法启动 / 健康检查失败 | 立即代码回滚（deploy-remote.sh 已自动触发；未自动则手动 §6.2） |
| 功能严重 Bug 影响主流程 | 当日回滚代码，修复后重新发布 |
| 数据异常（错算/损坏） | 停止写入 → 评估损失 → §4.2 恢复备份 或 §4.3 迁移回退 |
| 仅 UI/文案问题 | 不回滚，热修复随下版本发布 |

### 6.2 代码回滚（一键）

```bash
bash scripts/deploy-remote.sh --rollback
```

脚本自动：查找 `/tmp/X-backup-*.tar.gz` 最新备份 → 停服 → 恢复代码 → 重启 → 健康检查。

备份不可用时，用 GitHub 上一版本 tag 重建：

```bash
git checkout v<上一版本>
bash scripts/deploy-remote.sh --skip-push --skip-tag
git checkout main
```

### 6.3 数据库回滚

1. **优先迁移 down**（§4.3，保留新数据，需 down 已测试）
2. **整库恢复**（§4.2，回到备份时点，会丢失备份后写入）
3. 含迁移的版本回滚代码时**必须同步评估 schema**：旧代码 + 新 schema 通常向前兼容（新增列/表不影响），可暂缓回退 schema；但**回退后禁止再执行新迁移**，直至问题修复重新发布

### 6.4 GitHub 同步失败处理

部署脚本在 `git push` 阶段因网络超时失败时：

1. 继续完成部署（生产可用性优先）
2. 在发布记录中登记"待补推"
3. 网络恢复后补推：`git push origin main && git push origin vX.Y.Z`
4. 若部署依赖了未推送的迁移代码，**必须确保补推完成**后才算发布闭环

## 7. 应急预案

### 7.1 部署中途失败（脚本中断）

- 现象：上传后解压前断开、npm install 失败等
- 处置：服务器代码可能处于新旧混合状态 → 直接执行 `bash scripts/deploy-remote.sh --rollback`，或按 §3.3 重新完整部署一次

### 7.2 迁移执行失败（migrate.js 报错）

- 迁移在事务中执行，失败自动回滚该迁移，schema 保持前一版本
- 处置：
  1. 查看 `[Migration] 失败:` 报错信息与 `pm2 logs X-api`
  2. 本地测试库复现并修复迁移代码
  3. 修复代码走完整提交流程后重新部署、重新执行迁移（迁移幂等，可安全重跑）
- **禁止**：手动改生产 schema_migrations 记录或绕过迁移脚本直接执行 SQL

### 7.3 服务重启后持续 5xx

1. `pm2 logs X-api --err --lines 50` 定位报错
2. 常见原因：依赖未安装（新 package.json → 服务器需 `npm install --omit=dev`）、.env 缺变量、迁移未执行导致新代码查不到新列
3. 无法快速定位 → 回滚代码（§6.2），保留现场日志后再排查

### 7.4 数据库连接耗尽 / 锁等待

- 现象：API 超时、`Too many connections`、锁等待超时
- 处置：`pm2 restart X-api` 释放连接池；检查是否有未提交事务（`SHOW PROCESSLIST`）；大表 DDL 改为低峰执行

### 7.5 服务器磁盘打满

- `/tmp/X-backup-*` 与 `/root/db-backups/`、`/root/.pm2/logs/` 是主要占用
- 处置：清理 10 个版本之前的备份；`pm2 flush X-api` 清理日志；扩容后恢复轮转策略

### 7.6 应急联系与值守

- 生产发布后 30 分钟内为观察期，值守人员需关注错误日志与业务群反馈
- 发现异常按 §6.1 决策树处置；重大事故（数据丢失/长时间不可用）第一时间回滚并同步全员

## 9. 红线清单（违反即事故）

- ❌ 未做生产库备份就执行迁移
- ❌ 生产环境执行 `npm run db:reset` 或 DROP DATABASE
- ❌ 修改已发布的迁移或 schema_migrations 记录
- ❌ 绕过部署脚本直接覆盖服务器文件而不留代码备份
- ❌ 测试未通过强行部署
- ❌ 部署含敏感信息（.env/密码）的文件到服务器
- ❌ 回滚后未评估 schema 兼容性再次执行新迁移
