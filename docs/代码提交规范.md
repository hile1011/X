# 代码提交规范

> **版本**：V1.0
> **生效日期**：2026-09-06
> **适用项目**：报价跟单系统（quote-order-system）
> **配套文档**：[数据库版本管理规范](./数据库版本管理规范.md) · [部署规范](./部署规范.md)

---

## 1. 总则

### 1.1 目的

统一代码提交格式、分支管理策略与代码审查流程，保证每一次提交**语义清晰、可追溯、可回滚**，使数据库更新与日常开发部署保持一致性与安全性。

### 1.2 核心原则

| 原则 | 说明 |
|------|------|
| **原子提交** | 一次提交只做一件事（一个功能 / 一个修复 / 一类重构），不混合无关改动 |
| **语义化信息** | 提交信息必须说明"为什么改"，而不只是"改了什么" |
| **可编译可测试** | main 分支任意提交点必须通过 `npm run check` 与 `npm test`，禁止提交红码 |
| **版本可追溯** | 每次生产发布对应一个 git tag（`vX.Y.Z`）与一条 `chore(release)` 提交 |
| **迁移同步提交** | 涉及数据库变更时，迁移代码、全量脚本、测试必须在**同一个提交**中 |

## 2. 提交信息格式

### 2.1 格式定义

```
<type>(<scope>): <subject>

[body]

[footer]
```

- **type**（必填）：提交类型，见 §2.2
- **scope**（可选）：影响范围，如 `db`、`api`、`dashboard`
- **subject**（必填）：一句话概述，中文为主，不超过 50 字，结尾不加句号
- **body**（可选）：详细说明改动动机、实现要点，涉及数据库迁移时**必须**列出迁移版本与内容
- **footer**（可选）：关联事项，如 `Closes #12`、`迁移版本：v24`

### 2.2 提交类型（type）

| type | 用途 | 项目实际示例 |
|------|------|------------|
| `feat` | 新功能 | `feat: DB v17-v23 应收账款逻辑+款式模板一对多+客户标签` |
| `fix` | 缺陷修复 | `fix: 统一价格计算口径(保留2位小数)+修复日期解析时区偏移` |
| `style` | 样式/UI 适配（不改逻辑） | `style: 适配 antd v6 Select/TreeSelect 类名与 DOM 结构变化` |
| `refactor` | 重构（不改外部行为） | `refactor: 订单排序逻辑抽取为 quoteSort 工具函数` |
| `perf` | 性能优化 | `perf: 图片压缩串行处理，目标 200KB` |
| `test` | 测试补充/修正 | `test: 修复 sheetTemplates-page 测试选择器多元素匹配` |
| `docs` | 文档变更 | `docs: 新增代码提交规范与部署规范` |
| `chore` | 构建/工具/依赖/发布 | `chore(release): v1.1.25` |

### 2.3 提交信息模板

**常规功能提交**：

```
feat(<scope>): <功能概述>

- <模块1>：<改动点与动机>
- <模块2>：<改动点与动机>
- <模块3>：<改动点与动机>

测试：<新增/修改的测试文件与覆盖点>
```

**涉及数据库迁移的提交（body 必含迁移清单）**：

```
feat: DB vN[-vM] <业务概述>

迁移 vN <name>：<表/字段变更内容，DDL 还是 DML>
[迁移 vN+1 <name>：<...>]

数据迁移：<存量数据回填策略、分批大小、幂等性说明>

测试：<migration-*.test.ts 覆盖点（结构/种子/幂等/回滚/版本号）>
同步：db/schema/schema_vM.sql 全量脚本已更新
```

> 实际范例参见提交 `5a8255c`（DB v17-v23）。

**发布提交**：

```
chore(release): vX.Y.Z
```

发布提交只改 `package.json` 的 `version` 字段，与业务提交分开。

### 2.4 禁止事项

- ❌ 提交信息只有 `update`、`fix bug`、`修改` 等无语义内容
- ❌ 一次提交混合功能开发 + 格式化 + 依赖升级等无关改动
- ❌ 提交不能编译或测试不通过的代码到 main
- ❌ 提交 `.env`、密码、密钥、日志、构建产物（`dist/`、`api/dist/`）、`node_modules/`
- ❌ 迁移代码与全量脚本、测试分多次提交（会导致中间提交点无法通过测试）
- ❌ 修改或删除已发布 tag 对应的历史提交（force push 到 main）

## 3. 分支管理策略

### 3.1 分支模型（单主干 + 短周期特性分支）

本项目团队规模小、迭代快，采用**简化版主干开发**模式：

```
main ──────────●────●────●──●──────→  （始终可发布）
                \    \      /
feature/xxx     ●──●─●   ●─●           （短周期，1~3 天内合回）
hotfix/xxx            ●─●              （紧急修复，基于最新 main）
```

| 分支 | 命名规则 | 生命周期 | 说明 |
|------|---------|---------|------|
| `main` | — | 永久 | 唯一发布来源；任意提交点必须可编译、测试全绿；每次生产发布打 tag |
| `feature/<名称>` | `feature/order-templates`、`feature/gantt-tasks` | ≤ 3 天 | 从最新 main 拉出；完成后合回 main 并删除 |
| `hotfix/<名称>` | `hotfix/quote-insert-bug` | ≤ 1 天 | 仅用于生产紧急修复；基于 main，修复后立即合回并发布 |

### 3.2 分支操作规则

1. **禁止直接向 main 推送大型改动**——日常开发在 feature 分支进行；小型改动（文档、单行修复）可直接提交 main，但必须自测通过
2. **合并方式**：feature → main 使用 squash 或普通 merge，保留有意义的提交历史
3. **冲突处理**：feature 分支合入前先 `git rebase main` 或 `git merge main` 解决冲突并重跑测试
4. **同步远端**：合并后立即 `git push origin main`；GitHub 网络不可达时，可在部署完成后网络恢复时补推（参考部署规范 §6.4）

### 3.3 版本号与标签策略

- 版本号格式 `X.Y.Z`（语义化版本）：
  - **Z（修订号）**：缺陷修复、小调整（如 `1.1.23` → `1.1.24`）
  - **Y（次版本号）**：新功能、含数据库迁移的发布（如 `1.1.25`，DB v17-v23；`1.2.0` 可用于做货流程等大功能）
  - **X（主版本号）**：架构级变化时启用
- 每次生产发布必须：
  1. 更新 `package.json` 的 `version`
  2. 提交 `chore(release): vX.Y.Z`
  3. 打附注标签 `git tag -a vX.Y.Z -m 'Release vX.Y.Z'`
  4. 推送 main 与 tag 到 GitHub
- **数据库 Schema 版本与代码版本独立演进**（schema v24 ≠ 应用 v1.1.28），但发布提交信息中应注明本次包含的 schema 版本范围

## 4. 代码审查流程

### 4.1 流程步骤

```
开发者自检 → 提交 feature 分支 → 发起审查 → 审查者反馈 → 修正 → 合并 main
```

1. **开发者自检**（提交前必做，见 §5.1 检查清单）
2. **发起审查**：将 feature 分支名 + 改动摘要（git diff --stat）发给审查者；重要功能附设计文档（如 `docs/订单做货流程设计文档.md`）
3. **审查者范围**：同模块负责人或任意熟识该模块的成员；紧急修复可由作者自审后在提交信息中注明
4. **审查反馈**：按严重程度标记 `blocker`（必须改）/ `suggestion`（建议改）/ `nit`（可忽略）
5. **修正与合并**：blocker 全部解决后合并；审查记录保留在提交信息或会话记录中

### 4.2 审查要点

| 维度 | 检查内容 |
|------|---------|
| 正确性 | 业务逻辑是否符合需求；边界条件（null/空串/并发）是否处理 |
| 数据库 | 迁移是否幂等、是否有 down 函数、全量脚本是否同步（详见数据库版本管理规范） |
| 安全 | 权限校验（requirePermission）、输入校验、SQL 参数化、无硬编码敏感信息 |
| 测试 | 新逻辑有对应测试；测试与实现一起提交 |
| 一致性 | 前后端类型定义同步（api/types 与 src/types）；命名与既有代码风格一致 |
| 性能 | 大表操作分批（≤1000 行）；列表接口避免 N+1 查询 |

### 4.3 审查质量红线（出现即 blocker）

- 迁移缺 `down` 函数或全量脚本未同步
- 新增 API 路由无权限校验
- 提交包含敏感信息（.env / 密码 / 密钥）
- 删除或修改已发布的迁移
- 测试被跳过（skip/only）或断言被删以求通过

## 5. 质量标准

### 5.1 提交前检查清单（全部通过才可提交）

```bash
# 1. 类型检查：零错误零警告
npm run check        # tsc --noEmit

# 2. 单元测试：全部通过（不允许 skip）
npm test             # vitest run

# 3. 涉及数据库迁移时（附加）：
#    - tests/migration-*.test.ts 已编写并通过（覆盖结构/种子/幂等/回滚/版本号）
#    - tests/helpers/db-reset.ts 的 TABLES_TO_RESET 已包含新表
#    - db/schema/schema_vN.sql 全量脚本已同步
#    - 全量脚本可在空库执行（本地验证：见数据库版本管理规范 §验证）

# 4. 工作区干净：确认无 .env / 构建产物 / 日志误入暂存区
git status
```

### 5.2 质量指标

| 指标 | 标准 |
|------|------|
| TypeScript 编译 | `tsc --noEmit` 零错误零警告 |
| 单元测试 | 100% 通过；当前基线 36 文件 / 1088+ 用例，只增不减 |
| 迁移执行时间 | 单个迁移 < 30 秒（生产库） |
| 迁移幂等性 | up/down 重复执行不报错 |
| 新增表/权限 | 必须有对应迁移测试 + db-reset 登记 + 全量脚本条目 |

### 5.3 测试要求

- 新增业务逻辑（服务层/工具函数/组件）必须配套测试文件：
  - 数据库迁移 → `tests/migration-<name>.test.ts`
  - 页面组件 → `tests/<page>-page.test.tsx`
  - 纯逻辑模块 → `tests/<module>.test.ts`
- 测试命名使用中文描述业务意图，如 `it('回归：创建成功进入编辑器后返回列表，弹窗不再重复弹出')`
- Bug 修复必须附回归测试（先写失败用例再修复）

## 6. 提交流程示例（端到端）

```bash
# 1. 拉取最新代码
git checkout main && git pull origin main

# 2.（可选）功能分支
git checkout -b feature/production-tasks

# 3. 开发完成，自检
npm run check && npm test

# 4. 暂存（明确列出文件，避免 git add -A 误入敏感文件）
git add api/migrations/index.ts db/schema/schema_v24.sql \
        src/components/ProductionTasksTab.tsx tests/migration-production-tasks.test.ts

# 5. 提交（含迁移清单）
git commit -m "feat: 做货流程任务甘特图（DB v24）
...
"

# 6. 推送
git push origin main   # 或 git push origin feature/production-tasks
```
