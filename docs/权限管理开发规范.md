# 权限管理开发规范

> 适用范围：系统所有新增功能模块。完整权限目录见 [权限配置文档.md](./权限配置文档.md)。

## 核心原则

**任何新增功能默认纳入权限管理体系**。不允许出现"仅登录即可访问"的业务功能页面或写操作端点（登录页、健康检查等基础设施除外）。

## 一、新增功能时的权限实施步骤（必做）

### 1. 权限点定义

- 权限码格式 `模块:操作`，模块名用 kebab-case 英文（如 `production-tracking:view`）
- 每个功能模块至少定义一个 `模块:view`（menu 类型）作为入口权限
- 按操作粒度拆分 button 权限：`create` / `edit` / `delete` / 特殊操作（如 `execute`）
- 粒度适当：入口权限 + 高危写操作权限必拆；同类低风险操作可合并

### 2. 数据库迁移注册

在 `api/migrations/index.ts` 末尾新增迁移（遵循 [数据库版本管理规范](./数据库版本管理规范.md)）：

- `up` 用 `INSERT IGNORE INTO permissions` 插入权限目录（幂等）
- **必须为存量角色做兼容分配**：参照升级前该功能的等效权限，用
  `INSERT IGNORE INTO role_permissions ... SELECT ... WHERE p.code = '原权限'` 保持行为零回退
- admin 角色显式分配全部新权限
- `down` 必须提供：先删 `role_permissions` 关联，再删 `permissions`

### 3. 后端权限验证

- 业务端点必须挂权限中间件：`requirePermission('模块:操作')`
- 端点被多个模块复用时用 `requireAnyPermission('模块A:x', '模块B:x')`（参考 `GET /quotes/:id/production-tasks`）
- 权限判断发生在业务 handler **之前**，未持权限返回 403

### 4. 前端界面控制

- 路由守卫：`<ProtectedRoute permission="模块:view">`（src/App.tsx）
- 菜单显隐：`menuItems` 配置 `permission` 字段（src/components/Sidebar.tsx）
- 操作按钮：页面内 `const canXxx = hasPermission('模块:操作')` 控制渲染与只读态
- 权限管理/角色管理界面的 `moduleNames` 需补全新模块中文名（Permissions.tsx、Roles.tsx）

### 5. 测试与种子同步

- 新增 `tests/migration-*.test.ts`：覆盖权限结构、admin 分配、存量角色兼容、幂等、回滚
- `tests/helpers/db-reset.ts` 的 `SEED_PERMISSIONS` 同步新增权限
- 更新既有总数断言（migration-auth / rbac 中的权限计数）
- 组件测试的权限 mock 使用新权限码验证按钮显隐

### 6. 发布前检查

- [ ] `npm test` 全部通过
- [ ] `npx tsc --noEmit` 无错误
- [ ] `CURRENT_SCHEMA_VERSION` 已更新
- [ ] 权限配置文档目录表已更新
- [ ] 生产环境已备份数据库

## 二、禁止事项

- ❌ 新功能端点只挂 `authenticate` 不挂权限校验
- ❌ 前端隐藏按钮但后端无权限拦截（可被直接调 API 越权）
- ❌ 迁移 up 未做存量角色兼容分配（升级即丢失既有用户访问）
- ❌ 修改已发布迁移中的权限定义
- ❌ 硬编码权限码以外的"魔法判断"替代 RBAC（如按用户 email 判断）

## 三、既有功能权限梳理（持续）

- 发现复用他模块权限的功能（如早期做货跟踪复用 `quotes:view`），应通过迁移独立为专属模块权限并做存量兼容分配（参考 v30）
- 权限码重命名/拆分时须保持存量行为：新权限自动授予原等效持有者
